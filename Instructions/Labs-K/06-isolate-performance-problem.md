# 모니터링을 통한 성능 문제 격리

**예상 소요 시간: 30분**

### **랩(Lab)의 의미와 목표**

이 랩은 데이터베이스 관리자(DBA)의 핵심 업무 중 하나인 **성능 문제 해결**에 초점을 맞춥니다. 실제 운영 환경에서는 "데이터베이스가 느리다"라는 막연한 문제를 접하게 됩니다. 이 랩의 목표는 막연한 문제를 구체적인 데이터로 분석하고, 원인이 되는 쿼리를 정확히 찾아내는 과정을 배우는 것입니다.

*   **랩의 흐름**: 이 실습은 의사가 환자를 진단하는 과정과 유사합니다.
    1.  **문제 상황 재현**: 의도적으로 데이터베이스에 부하를 주는 쿼리를 실행하여 '아픈' 상태를 만듭니다.
    2.  **증상 확인**: Azure Portal의 **메트릭(Metrics)** 기능을 사용하여 CPU 사용률이 급증하는 '증상'을 시각적으로 확인합니다.
    3.  **정밀 진단**: **Query Performance Insight**라는 전문 진단 도구를 사용하여 CPU 사용률을 높인 '정확한 원인(쿼리)'을 찾아냅니다.
*   **핸즈온(Hands-on)의 중요성**: 이 랩을 통해 DBA가 Azure 환경에서 제공하는 기본 모니터링 도구를 사용하여 어떻게 성능 문제를 체계적으로 분석하고 해결하는지에 대한 실질적인 경험을 쌓게 됩니다. 이론으로만 알던 개념을 실제 데이터와 그래프를 통해 눈으로 확인하는 것이 핵심입니다.


**실습 목표:**
수강생들은 이전 강의에서 얻은 정보를 활용하여 AdventureWorksLT 내의 디지털 전환 프로젝트를 위한 결과물의 범위를 정합니다. Azure Portal 및 기타 도구를 검토하면서, 성능 관련 문제를 식별하고 해결하기 위해 도구를 활용하는 방법을 결정합니다.

**시나리오:**
당신은 성능 관련 문제를 식별하고 발견된 문제를 해결하기 위한 실행 가능한 솔루션을 제공하는 데이터베이스 관리자로 고용되었습니다. Azure Portal을 사용하여 성능 문제를 식별하고 이를 해결하기 위한 방법을 제안해야 합니다.

> &#128221; 이 연습에서는 T-SQL 코드를 복사하여 붙여넣고 기존 SQL 리소스를 사용해야 합니다. 코드를 실행하기 전에 코드가 올바르게 복사되었는지 확인하십시오.

## Azure Portal에서 CPU 사용률 검토

**핸즈온 의미**: 이제 본격적인 성능 진단의 첫 단계입니다. 의도적으로 부하를 발생시킨 후, Azure Portal의 기본 모니터링 도구인 **메트릭(Metrics)**을 사용하여 시스템의 반응(CPU 사용률 급증)을 시각적으로 확인합니다. 이는 문제의 존재를 객관적인 데이터로 확인하는 과정입니다.

1.  랩 가상 머신 또는 제공되지 않은 경우 로컬 머신에서 브라우저 세션을 시작하고 [https://portal.azure.com](https://portal.azure.com/)으로 이동합니다. Azure 자격 증명을 사용하여 포털에 연결합니다.

2.  Azure Portal 상단의 검색창에서 *SQL 서버*를 검색한 다음, 옵션 목록에서 **SQL 서버**를 선택합니다.

3.  SQL 서버 **dp300-lab-xxxxxxxx**를 선택합니다. 여기서 *xxxxxxxx*는 임의의 숫자 문자열입니다.

    > &#128221; 참고: 이 랩에서 생성하지 않은 자신의 Azure SQL 서버를 사용하는 경우, 해당 SQL 서버의 이름을 선택하십시오.

4.  Azure SQL 서버 기본 페이지의 **보안** 아래에서 **네트워킹**을 선택합니다.

5.  **네트워킹** 페이지에서 현재 공인 IP가 이미 **방화벽 규칙** 목록에 추가되었는지 확인하고, 그렇지 않은 경우 **+ 클라이언트 IPv4 주소 추가(사용자 IP 주소)**를 선택하여 추가한 다음 **저장**을 선택합니다.

6.  Azure SQL 서버의 기본 블레이드에서 **설정** 섹션으로 이동하여 **SQL 데이터베이스**를 선택한 다음, **AdventureWorksLT** 데이터베이스를 선택합니다.

7.  왼쪽 탐색 메뉴에서 **쿼리 편집기(미리 보기)**를 선택합니다.

    **참고:** 이 기능은 미리 보기(preview) 상태입니다.

    > **용어 및 의미 설명**: **쿼리 편집기(Query Editor)**는 SSMS와 같은 별도의 도구를 설치하지 않고도 Azure Portal 내에서 직접 데이터베이스에 연결하고 T-SQL 쿼리를 실행할 수 있는 웹 기반 도구입니다. 간단한 쿼리 테스트나 데이터 확인에 매우 유용합니다.

8.  SQL Server 관리자 사용자 이름을 선택하고 암호를 입력하거나, 할당된 경우 Microsoft Entra 자격 증명을 사용하여 데이터베이스에 연결합니다.

9.  **쿼리 1**에 다음 쿼리를 입력하고 **실행**을 선택합니다:

    ```sql
    DECLARE @Counter INT 
    SET @Counter=1
    WHILE ( @Counter <= 10000)
    BEGIN
        SELECT 
             RTRIM(a.Firstname) + ' ' + RTRIM(a.LastName)
            , b.AddressLine1
            , b.AddressLine2
            , RTRIM(b.City) + ', ' + RTRIM(b.StateProvince) + '  ' + RTRIM(b.PostalCode)
            , CountryRegion
            FROM SalesLT.Customer a
            INNER JOIN SalesLT.CustomerAddress c 
                ON a.CustomerID = c.CustomerID
            RIGHT OUTER JOIN SalesLT.Address b
                ON b.AddressID = c.AddressID
        ORDER BY a.LastName ASC
        SET @Counter  = @Counter  + 1
    END
    ```
    > **핸즈온 의미**: 이 쿼리는 **WHILE 루프**를 사용하여 동일한 SELECT 문을 **10,000번 반복**합니다. 쿼리 자체는 복잡하지 않지만, 짧은 시간 동안 극도로 많이 실행되도록 하여 의도적으로 CPU에 높은 부하를 발생시킵니다. 이는 비효율적인 애플리케이션 로직이 데이터베이스에 어떤 영향을 미치는지 시뮬레이션하는 것입니다.

10. 쿼리가 완료될 때까지 기다립니다.

11. 데이터베이스에 CPU 부하를 발생시키기 위해 쿼리를 *두 번 더* 다시 실행합니다.

12. **AdventureWorksLT** 데이터베이스의 블레이드에서 **모니터링** 섹션의 **메트릭** 아이콘을 선택합니다.

    *저장되지 않은 변경 내용은 무시됩니다*라는 팝업이 나타나면 **확인**을 선택합니다.

13. **메트릭** 메뉴 옵션을 **CPU 백분율**로 변경한 다음, **집계**를 **평균(Avg)**으로 선택합니다. 이렇게 하면 주어진 시간 프레임에 대한 평균 CPU 백분율이 표시됩니다.

14. 시간 경과에 따른 CPU 평균을 관찰합니다. 쿼리가 실행되었던 그래프의 끝부분에서 CPU 사용률이 급증하는 것을 확인할 수 있어야 합니다.

## 높은 CPU를 유발하는 쿼리 식별

**핸즈온 의미**: 이 섹션은 이 랩의 핵심입니다. CPU 사용률이 높다는 '증상'을 확인했으니, 이제 **Query Performance Insight(QPI)** 라는 전문 진단 도구를 사용하여 어떤 쿼리가 그 원인인지 정확히 '진단'합니다. QPI는 Azure SQL Database에 내장된 **Query Store**의 데이터를 시각화하여 가장 많은 리소스를 소비한 쿼리를 순위별로 보여줍니다.

1.  **AdventureWorksLT** 데이터베이스 블레이드의 **지능형 성능(Intelligent Performance)** 섹션에서 **Query Performance Insight** 아이콘을 찾습니다.

2.  **설정 재설정**을 선택합니다.

3.  그래프 아래의 그리드에서 쿼리를 선택합니다. 이전에 여러 번 실행했던 쿼리가 보이지 않으면 2~5분 정도 기다렸다가 **새로 고침**을 선택합니다.

    > &#128221; 둘 이상의 쿼리가 나열된 경우, 각각을 선택하여 결과를 관찰하십시오. 각 쿼리에 대해 풍부한 정보가 제공된다는 점에 유의하십시오.

4.  이전에 실행한 쿼리에 대해 총 실행 시간이 1분이 넘고 약 3만 번 실행되었다는 점에 주목하십시오.

5.  **쿼리 세부 정보** 페이지의 SQL 텍스트를 실행한 쿼리와 비교해 보면, **쿼리 세부 정보**에는 **WHILE** 루프나 다른 문장이 아닌 **SELECT** 문만 포함되어 있음을 알 수 있습니다. 이는 **Query Performance Insight**가 **Query Store**의 데이터에 의존하기 때문입니다. Query Store는 **SELECT, INSERT, UPDATE, DELETE, MERGE, BULK INSERT**와 같은 데이터 조작 언어(DML) 문만 추적하고 데이터 정의 언어(DDL) 문은 무시합니다.

**결론**: 모든 성능 문제가 단일 쿼리 실행의 높은 CPU 사용률과 관련된 것은 아닙니다. 이 경우처럼, 쿼리가 수천 번 실행되어 높은 CPU 사용률을 초래할 수도 있습니다.

## 리소스 정리

(이전 랩의 번역과 동일하며, 정리 대상에 로컬 파일 폴더 삭제가 추가됨)

Azure SQL Server를 다른 용도로 사용하지 않는다면, 이 랩에서 생성한 리소스를 정리할 수 있습니다.

### 리소스 그룹 삭제

이 랩을 위해 새 리소스 그룹을 만들었다면, 리소스 그룹을 삭제하여 이 랩에서 생성된 모든 리소스를 제거할 수 있습니다.

1.  Azure Portal의 왼쪽 탐색 창에서 **리소스 그룹**을 선택하거나 검색창에서 검색합니다.
2.  이 랩을 위해 생성한 리소스 그룹으로 들어갑니다.
3.  상단 메뉴에서 **리소스 그룹 삭제**를 선택합니다.
4.  대화 상자에서 리소스 그룹 이름을 입력하여 확인하고 **삭제**를 선택합니다.
5.  리소스 그룹이 삭제될 때까지 기다립니다.
6.  Azure Portal을 닫습니다.

### 랩 리소스만 삭제

새 리소스 그룹을 만들지 않고 기존 리소스를 유지하려면, 이 랩에서 생성한 리소스만 삭제할 수 있습니다.

1.  Azure Portal에서 **리소스 그룹**으로 이동합니다.
2.  이 랩에서 사용한 리소스 그룹으로 들어갑니다.
3.  랩에서 지정한 SQL 서버 이름으로 시작하는 모든 리소스를 선택합니다.
4.  상단 메뉴에서 **삭제**를 선택합니다.
5.  대화 상자에서 **delete**를 입력하고 **삭제**를 선택합니다.
6.  삭제를 다시 확인합니다.
7.  리소스가 삭제될 때까지 기다립니다.
8.  Azure Portal을 닫습니다.

### LabFiles 폴더 삭제

이 랩을 위해 새 LabFiles 폴더를 만들었고 더 이상 필요하지 않은 경우, LabFiles 폴더를 삭제하여 이 랩에서 생성된 모든 파일을 제거할 수 있습니다.

1.  랩 가상 머신 또는 제공되지 않은 경우 로컬 머신에서 파일 탐색기를 열고 **C:\\** 드라이브로 이동합니다.
2.  **LabFiles** 폴더를 마우스 오른쪽 버튼으로 클릭하고 **삭제**를 선택합니다.
3.  **예**를 선택하여 폴더 삭제를 확인합니다.
